# ТЗ (реализация): Git-based bootstrap Linux VPS через cloud-init и Ansible

Этот файл описывает конкретную техническую реализацию требований из AI-brief.md.
При изменениях в ходе работы правки вносятся синхронно в оба файла.

Название проекта и репозитория - `cloud-init-ansiblepull` (remote: `github.com/nvsmirnov/cloud-init-ansiblepull`).

## Общая схема

- Вся bootstrap-логика описывается в самом `user-data` (cloud-config), без отдельного `bootstrap.sh`.
- Ansible ставится через top-level ключ `packages:`, а `ansible-pull` запускается через `runcmd:` - оба стандартных, универсальных механизма cloud-init, не завязанных на модуль `ansible` (`cc_ansible`). Почему не `cc_ansible` - см. "Установка Ansible" ниже.
- Отдельный скрипт-загрузчик не нужен: `packages:` + `runcmd:` целиком закрывают cadence "install ansible -> ansible-pull", описанный в AI-brief.md, средствами самого cloud-init.

## Установка Ansible

- **Модуль `ansible` (`cc_ansible`) не используется.** Причина - не гипотетическая, а найдена на реальном примере: в `/etc/cloud/cloud.cfg` с AWS-инстанса на Amazon Linux модуль `ansible` вообще отсутствует в списке `cloud_final_modules` (в отличие от Ubuntu 26.04, где он есть). Список модулей в cloud.cfg - это whitelist: модуль, которого там нет, не запускается вообще, независимо от того, что написано в user-data. Проверено эмпирически: с `cloud_final_modules`, скопированным один в один с реального AWS-образа, ключ `ansible:` в user-data полностью игнорируется - `cloud-init status` при этом рапортует `errors: []`, полный успех, а bootstrap просто не происходит. Это не баг конкретного образа, а следствие того, что каждый провайдер/образ волен кастомизировать этот список по-своему - полагаться на присутствие в нём именно `ansible` небезопасно.
- Вместо этого: `packages: [git, ansible-core]` (ставит пакеты штатным пакетным менеджером, через `Distro.install_packages()` - тот же механизм, что раньше давал `install_method: distro`) + `runcmd:` с прямым вызовом `ansible-pull --url=... --checkout=... ansible/playbook.yml`.
- Оба модуля, обеспечивающих `packages:` и `runcmd:` (`package_update_upgrade_install` и `scripts_user` соответственно), присутствуют **и на Ubuntu 26.04, и на реальном AWS-образе** - в отличие от `ansible`, которого нет на AWS. Это старые, базовые модули cloud-init, значительно менее вероятно, что их выкинут из кастомного списка модулей, чем сравнительно нишевый `ansible`. Проверено эмпирически на обоих списках модулей (Ubuntu 26.04 "как есть" и AWS-список 1:1) - в обоих случаях `packages:`+`runcmd:`-вариант отрабатывает: маркер записан, `errors: []`.
- **Критично: первой строкой в `runcmd:` обязателен `set -e`.** Сгенерированный cloud-init скрипт для `runcmd:` - обычный `#!/bin/sh` без `set -e` по умолчанию. Без него упавший `ansible-pull` не останавливает скрипт (следующие команды всё равно выполняются) и не отражается в `cloud-init status` вообще (`errors: []`, как будто всё прошло успешно) - это худший silent-failure, чем тот, который эта смена архитектуры устраняла. Проверено эмпирически: тот же сценарий с `set -e` первой строкой корректно останавливает скрипт и даёт `status: error`, непустой `errors:`, exit code 1.
- Роли выбираются через `-e "roles=web,db"` флаг самого `ansible-pull` (вместо YAML-ключа `extra_vars` у `cc_ansible`) - для `playbook.yml` эффект идентичен, переменная `roles` точно так же попадает в extra-vars.
- Побочный плюс: `git` теперь явно объявлен зависимостью прямо в user-data (`packages:`), а не молчаливо предполагается присутствующим на образе - раньше этот пробел был закрыт только для `scripts/manual.sh` (generic-Linux случай), но не для VPS-шаблонов.
- Компромисс остаётся прежним: версия Ansible - та, что идёт с дистрибутивом (для Ubuntu 26.04 сейчас `ansible-core` 2.20.1), а не последняя с PyPI. Осознанно принято, см. "Целевые дистрибутивы" - проект должен опираться на простые, стабильные Ansible-фичи, а не гнаться за последней версией.
- На Ubuntu пакет `ansible-core` тянет через `Recommends` 20 лишних пакетов (34 устанавливается с Recommends против 14 без них, проверено через `apt-get install --simulate`): полный метапакет `ansible` (community collections, ~216 МБ) плюс мелкие WinRM/Kerberos/SELinux/libcloud/X11-плагины (~14 МБ) - apt по умолчанию ставит Recommends. Суммарно ~224 МБ лишнего, посчитано через `Installed-Size`. Это не специфика `cc_ansible` - тот же эффект будет при установке `ansible-core` через `packages:`, поскольку оба пути ведут к одному и тому же `apt-get install` без `--no-install-recommends`. Для VPS это осознанно не устраняется (см. ниже), для generic-Linux случая (`scripts/manual.sh`) - устраняется через `autoremove`.
- Осознанно решено не обходить это через apt-специфичные хаки (например `bootcmd`/`runcmd` с ручным `--no-install-recommends`) в самих VPS-шаблонах: это захардкодило бы apt в месте, которое должно оставаться distro-агностичным. ~224 МБ лишних пакетов не опасны (не сервис, не демон, не конфликтует с PATH) - просто лишние байты на диске постоянно работающего VPS, что приемлемо в отличие от one-shot generic-Linux случая (там `scripts/manual.sh` явно чистит их, апт-специфичность там осознанно допустима, см. ниже).

### Почему был откинут cc_ansible (историческая справка)

Первая реализация использовала `ansible:`/`cc_ansible` (`install_method: pip`, затем `install_method: distro`). По пути были найдены и обойдены несколько проблем самого `cc_ansible`, все они теперь неактуальны, так как модуль больше не используется, но фиксируются здесь, чтобы никто не предлагал вернуться к нему не зная предыстории:

- `install_method: pip` без `run_user` ставил пакет в системные `dist-packages` через `--break-system-packages` (PEP 668); с `run_user` команды шли через `su - root`, а логин-шелл `root` не подхватывает `$HOME/.local/bin` в PATH - требовался отдельный PATH-фикс через `write_files`.
- `install_method: distro` избавлял от этого (штатный пакетный менеджер, `run_user` не нужен), но всё ещё зависел от того, что модуль `ansible` присутствует в `cloud_final_modules` - что и оказалось решающей проблемой на AWS.
- Штатного способа передать `--no-install-recommends` в собственный `apt-get install` модуля `ansible` не было: ключ `apt_get_command` читается только из устаревшего `system_info:` (`Deprecated in version 24.2`), и в этой версии cloud-init он вдобавок ведёт к `AttributeError` в `Apt.__init__` (`self.apt_get_command` присваивается только в ветке `if apt_get_command is None`, без `else`) - креш всего пайплайна при попытке задать этот ключ.
- Самоудаление `ansible-core` из-под самого себя (см. ниже) было и остаётся невозможным - этот вывод не зависит от того, каким способом `ansible-core` был установлен, поэтому он вынесен в отдельный пункт ниже, не в историческую справку.

## Целевые дистрибутивы

- Проект не привязан к одному дистрибутиву. Минимальный набор, который должен поддерживаться в перспективе: свежие Ubuntu, Debian, RHEL-семейство, Amazon Linux, Alpine.
- `packages:` предпочтительнее pip для этого: у каждого дистрибутива штатный пакетный менеджер сам знает, как ставить `ansible-core` (или его аналог) без обходных путей, через тот же `Distro.install_packages()`.
- Playbook и роли должны использовать простые, портируемые фичи Ansible (например `ansible.builtin.package`, а не apt/dnf-специфичные модули напрямую), т.к. плейбук выполняется на той версии Ansible, которая пришла с дистрибутивом, а не на конкретной pinned версии.
- Сейчас реализация и smoke-тест покрывают только Ubuntu 26.04 LTS. Поддержка остальных дистрибутивов (включая корректный список пакетов для каждого - на RHEL/Amazon Linux и Alpine имя пакета может отличаться от `ansible-core`) - задача на будущее, не реализуется сейчас.

## ansible-pull и pin revision

- `url`/`checkout`/playbook - все передаются как обычные CLI-флаги `ansible-pull` внутри `runcmd:`, а не через YAML-ключи модуля `ansible`.
- `checkout` - pin на git revision. На старте два шаблона user-data:
  - `base.yaml` - `--checkout=main`.
  - `base-dev.yaml` - `--checkout=dev`.
- Pin на полный commit SHA - усложнение на будущее, если потребуется.
- Playbook (`ansible/playbook.yml`) передаётся последним позиционным аргументом `ansible-pull`.
- Inventory отдельно не настраивается, `ansible-pull` всегда работает по localhost. Поэтому entry-point playbook должен использовать `hosts: localhost`, а не `hosts: all` - при `hosts: all` play молча пропускается целиком (пустой PLAY RECAP, без ошибки), проверено эмпирически.

## Выбор ролей

- Универсального runtime-механизма передачи параметров сверх user-data нет, поэтому список ролей задаётся прямо в `runcmd:` через флаг `-e "roles=web,db"` у `ansible-pull`.
- `roles_to_apply` в `playbook.yml`: `(roles | default('base')) | split(',') | reject('equalto', '') | list`. Если флаг `-e "roles=..."` вообще не передан - подставляется `base` (единственная роль, которая раньше была захардкожена в `roles:` play-уровня). Если передан - это **полный список на замену**, а не добавка к `base`: если нужен и `base`, и что-то ещё, `base` указывается в списке явно (`-e "roles=base,web,db"`). Так пользователь явно решает, нужен ли ему `base` вообще, а не получает его безусловно.
- Раньше `base` был отдельной записью в `roles:` play-уровня, а остальные роли подключались через `include_role` в `tasks:`. Это давало баг: `roles:` в play выполняются раньше `tasks:` независимо от их взаимного порядка в YAML, поэтому `base`-роль пыталась писать свой `role-done-base` маркер до того, как `pre_tasks:` создавал `/var/lib/cloud-init-ansiblepull/` (тот таск жил в `tasks:`, позже `roles:`) - падение с `Destination directory ... does not exist`, проверено эмпирически. Исправлено переносом создания каталога/README в `pre_tasks:` (гарантированно раньше `roles:`), а затем и вовсе устранено переводом `base` в общий список `roles_to_apply`, подключаемый через тот же `include_role` в `tasks:`, что и остальные роли - больше нет двух разных путей подключения ролей с разным порядком выполнения.
- Плейбук в репозитории читает переменную `roles_to_apply` и включает соответствующие роли.
- Для разных наборов ролей достаточно скопировать шаблон user-data и добавить/поменять в нём `-e "roles=..."` в строке `ansible-pull`, отдельного механизма подстановки параметров не создаём.

## Структура репозитория

- `ansible/playbook.yml` — точка входа для `ansible-pull`.
- `ansible/roles/` — роли конфигурации.
- `ansible/requirements.yml` — внешние роли/коллекции с Galaxy, если понадобятся.
- `user-data/` — шаблоны cloud-config для VPS: `base.yaml` (`--checkout=main`), `base-dev.yaml` (`--checkout=dev`), `base-extended.yaml` (`base`+`extended`, для VPS, на которой предполагается интерактивно работать), `alpine.yaml` (пример под Alpine - те же роли плюс строка установки `community.general`, см. ниже), `test-all.yaml` (конфиг, на котором по умолчанию гоняется smoke-тест). Часть этих файлов сейчас побайтово совпадает - это осознанно, файлы разделены по назначению, а не по текущему содержимому. `scripts/manual.sh` эти шаблоны не использует (см. "Use-case: преднастройка generic Linux"). Дополнительные шаблоны (pin на SHA и т.п.) добавляются позже по потребности.
- `scripts/manual.sh` — ручной bootstrap для generic-Linux случая (не VPS), см. раздел "Use-case: преднастройка generic Linux" ниже.
- `tests/` — smoke-тест и всё для его запуска в Docker: `tests/run.sh` (один образ), `tests/test-all.sh` (прогон по всем поддерживаемым образам с итоговой сводкой; по умолчанию останавливается на первом упавшем, `NO_STOP_ON_FIRST_FAIL=1` прогоняет всё), `tests/Dockerfile`, `tests/stage-runner.sh`, `tests/seed-template/`.
- `AI-docs/` — этот файл, `AI-brief.md` и `AI-readme.md` (AI-authored документация, см. `AI-readme.md` про разделение с корневым `README.md`).

## Тестирование (Docker smoke-test)

- Требования: без `--privileged`, без systemd, без полноценной VM.
- Внутри контейнера запускается настоящий бинарник `cloud-init`, а не имитация его логики. Базовый образ - `BASE_IMAGE` (переменная окружения `tests/run.sh`, по умолчанию `ubuntu:latest`, передаётся в `docker build` как `--build-arg`), например `BASE_IMAGE=alpine:latest tests/run.sh ...`. `tests/Dockerfile` определяет пакетный менеджер образа по наличию `apt-get`/`dnf`/`apk` (`command -v`) и ставит bootstrap-зависимости (`cloud-init`, `git`, `ca-certificates`, плюс `lsb-release` только на apt-ветке для `cc_apt_configure`, плюс `bash` только на apk-ветке - в базовом образе Alpine его нет, а скрипты репозитория используют `#!/bin/bash`) соответствующим способом - проверено на `amazonlinux:latest`, `alpine:latest`, `debian:latest`, `ubuntu:latest`, `ubuntu:24.04`, `fedora:latest` (первые пять - список `SUPPORTED_IMAGES` в `tests/test-all.sh`). Образ без ни одного из известных пакетных менеджеров падает на этапе `docker build` с понятной ошибкой. Разброс версий cloud-init между образами большой: Amazon Linux 2023 несёт 22.2.2 на Python 3.9, Ubuntu/Fedora - 26.1.
- Проверено эмпирически на `alpine:latest` и `fedora:latest`: контейнер без реального init-процесса в роли PID 1 (что и требуется правилами теста - "без systemd, без --privileged, без VM") не может управлять сервисами через `ansible.builtin.service` - падает одинаково что на Alpine/OpenRC (`Could not find the requested service nginx: host`), что на Fedora/systemd (`Service is in unknown state`). Это ограничение тестового окружения, а не баг роли/плейбука - на реальной машине с настоящим init эта же роль отрабатывает штатно. Поэтому дефолтный шаблон для `tests/run.sh` - `user-data/test-all.yaml`, куда включаются только роли без управления сервисами; роль `nginx` по этой же причине сейчас не подключена ни к одному шаблону и остаётся просто примером роли в `ansible/roles/nginx/`.
- **Amazon Linux: модуль `selinux` в `cloud_init_modules` ломает прогон в контейнере, вырезается в `tests/Dockerfile`.** Проверено эмпирически: на `amazonlinux:latest` (cloud-init 22.2.2) стадия `cloud-init init` завершается с кодом 1, из-за чего `stage-runner.sh` (там `set -e`) обрывается ещё до первой своей проверки. Причина - AL-специфичный модуль `cc_selinux`: он парсит вывод `sestatus` в поисках `Current mode`, а в контейнере SELinux недоступен, ключа нет, модуль падает с `KeyError('current_mode')`. `cloud-init status --long` после этого показывает `status: error` с `('selinux', KeyError('current_mode'))` и код возврата 1 - то есть даже без `set -e` тест бы не прошёл по существующей проверке "hard error". Это именно специфика Amazon Linux: в `/etc/cloud/cloud.cfg` на `fedora:latest` модуля `selinux` нет вовсе, поэтому Fedora проходила, а AL - нет. При этом сам тестируемый bootstrap на Amazon Linux полностью исправен - при прогоне всех четырёх стадий с игнорированием кодов возврата получаем `PLAY RECAP ok=15 changed=12 failed=0`, без ошибок Ansible, со всеми маркерами (`all-done`, `role-done-base`, `role-done-extended`). Решение - вырезать строку `- selinux` из `/etc/cloud/cloud.cfg` в `tests/Dockerfile` (`sed -i`): это правка только тестовой обвязки, в том же духе, что и `network-config: disabled` в seed-каталоге и `safe.directory '*'`; на образах без этого модуля sed - no-op, поэтому ветвление по образам не нужно. Осознанно НЕ стали вместо этого ослаблять обработку ошибок в `stage-runner.sh` (игнорирование кодов возврата стадий замаскировало бы и настоящие поломки) и НЕ стали использовать drop-in в `cloud.cfg.d` (переопределение `cloud_init_modules` там заменяет список целиком и ломалось бы при расхождении версий cloud-init между образами).
- Alpine отдельно: `ansible.builtin.package` не умеет в `apk` - модуль `apk` есть только в коллекции `community.general`, которую проект сознательно не тянет через `ansible-pull` (усложнило бы синтаксис вызова и тянуло бы коллекцию безусловно даже туда, где она не нужна). Из-за того, что резолвер модулей/коллекций Ansible кэшируется на старте процесса, поставить коллекцию `pre_tasks`-шагом внутри самого плейбука не получилось - проверено эмпирически: коллекция ставится успешно, но следующая же задача с `ansible.builtin.package` падает с той же ошибкой, что и без установки вовсе. Рабочее решение - установить `community.general` отдельным шагом ДО запуска `ansible-pull`, вне плейбука: в `scripts/manual.sh` это условный шаг (`if [ "$PKG_FAMILY" = apk ]; ...`), в user-data-шаблонах (`base-extended.yaml`, `alpine.yaml`, `test-all.yaml`) - условная строка в `runcmd:` (`if command -v apk ...; then ansible-galaxy collection install community.general; fi`) перед строкой `ansible-pull` - ни то, ни другое не усложняет сам вызов `ansible-pull` и не тянет коллекцию на apt-/dnf-системах.
- `ansible-pull` внутри контейнера тянет не сам `$REPO_ROOT` напрямую, а одноразовый снэпшот текущего рабочего дерева: `tests/run.sh` собирает через `git ls-files --cached --others --exclude-standard` полный список файлов (tracked + untracked-но-не-игнорируемые), копирует их в одноразовый `git`-репозиторий во временном каталоге и делает там ровно один commit (ветка называется как в `--checkout=` тестируемого шаблона) - реальная история/ветки основного репозитория при этом не трогаются вообще. `git clone` физически не может увидеть незакоммиченные изменения (клонирует только объекты `.git`), поэтому раньше тест требовал реального коммита в `main` перед каждым прогоном; теперь коммит не нужен - тестируется буквально то, что лежит в рабочем дереве прямо сейчас.
- User-data подсовывается в том же формате, что и в проде, через NoCloud datasource с локальным seed-каталогом:
  - `/var/lib/cloud/seed/nocloud/user-data` — тестируемый шаблон user-data.
  - `/var/lib/cloud/seed/nocloud/meta-data` — минимальный файл с `instance-id`.
  - Само наличие этого каталога достаточно для активации NoCloud datasource, сеть и внешний metadata-сервис не нужны.
- Стадии boot нормально запускаются systemd-юнитами (`cloud-init-local.service`, `cloud-init.service`, `cloud-config.service`, `cloud-final.service`), но без systemd в контейнере эти же стадии вызываются вручную теми же командами, которые эти юниты используют:
  - `cloud-init init --local`
  - `cloud-init init`
  - `cloud-init modules --mode=config`
  - `cloud-init modules --mode=final`
- И `packages:` (модуль `package_update_upgrade_install`), и фактическое исполнение `runcmd:` (модуль `scripts_user`) относятся к **final**-модулям на обоих проверенных списках (Ubuntu 26.04 и AWS) - `--mode=final` обязателен, `--mode=config` тоже нужен (он пишет сгенерированный `runcmd`-скрипт на диск, исполняет его позже `scripts_user` в final-стадии).
- Проверки после прогона:
  - `cloud-init status` без hard error. Код возврата: 0 - чисто, 1 - реальная ошибка (fail), 2 - degraded/только warnings (допустимо в контейнере без systemd: генерация ssh host key, `hostnamectl` и т.п.). Критерий провала теста - код возврата 1, а не "код возврата не 0".
  - Playbook отработал: файл `/var/lib/cloud-init-ansiblepull/all-done` присутствует (пишется финальной задачей `playbook.yml` после того, как отработали все роли). Каждая роль дополнительно пишет свой маркер `/var/lib/cloud-init-ansiblepull/role-done-<имя роли>` - smoke-тест их по отдельности не проверяет, финального маркера достаточно.
  - Idempotency-check: повторный запуск того же `ansible-pull ...`, что и в `runcmd:`, не сообщает об изменениях. Технически - `stage-runner.sh` напрямую перезапускает сгенерированный cloud-init'ом скрипт `/var/lib/cloud/instances/*/scripts/runcmd` (тот же файл, что уже выполнил `scripts_user`), проверяя `changed=0 failed=0` в его собственном `PLAY RECAP`. Старый способ (`cloud-init single --name ansible ...`) относился к `cc_ansible` и больше не применим.

## Явные ограничения (перенесено из AI-brief.md)

- Не используется `curl | sh`.
- Не используется Ansible push-mode, SSH inventory, Terraform provisioners, Packer, LXC/LXD.
- Не требуется постоянно работающий агент/сервис на сервере.
- Systemd в тестовом окружении не используется, стадии cloud-init вызываются напрямую.

## Use-case: преднастройка generic Linux (не только VPS)

- Механизм отличается от VPS-кейса: cloud-init здесь вообще не используется. `scripts/manual.sh` ставит `git`/`ansible-core` (если их ещё нет) и напрямую запускает `ansible-pull` - без NoCloud, без seed-каталога, без стадий cloud-init. Раньше (до отказа от cloud-init в этом скрипте) использовался тот же приём, что и в Docker smoke-test; сейчас это упрощено, т.к. cloud-init здесь был не более чем обвязкой поверх `ansible-pull`, ничего специфичного для generic-Linux случая не добавлял.
- Целевая система для этого use-case совпадает с целевыми дистрибутивами проекта в целом, см. раздел "Целевые дистрибутивы". Сейчас Docker smoke-тестом покрыт только Ubuntu 26.04 (через `tests/run.sh`); `scripts/manual.sh` при этом дополнительно поддерживает apk-based (Alpine) системы, не покрытые smoke-тестом.
- Отдельного шаблона user-data под этот use-case больше не нужно - `scripts/manual.sh` не работает с user-data/cloud-config вообще, только с `-e "roles=..."` через переменную `ROLES`.
- Реализовано как `scripts/manual.sh`: `curl -o manual.sh ... && bash manual.sh`, тот же паттерн curl-скачал-запусти, что изначально предполагался для VPS в AI-brief.md (там не понадобился, пригодился здесь). Без cmdline-параметров: `REPO_URL` (git-URL репозитория, по умолчанию `https://github.com/nvsmirnov/cloud-init-ansiblepull.git`), `REPO_CHECKOUT` (по умолчанию `main`) и `ROLES` (по умолчанию не задана - т.е. `ansible-pull` вызывается без `-e roles=...`, и `ansible/playbook.yml` сам подставляет свой дефолт `base`, см. "Выбор ролей") - обычные env-переменные с default-значением через `${VAR:-default}`, как и всё остальное в скрипте.
- Скрипт поддерживает apt-based, dnf-based (RHEL-семейство) и apk-based (Alpine) системы - внутри он абстрагирует пакетный менеджер через набор `pkg_*`-функций (`pkg_is_installed`, `pkg_install`, `pkg_purge`, `pkg_autoremove_list_empty`, `pkg_autoremove`, `pkg_clean`), выбираемых по `${ID_LIKE:-${ID}}` из `/etc/os-release`: `debian` в этой строке -> apt/dpkg, `rhel`/`fedora` -> dnf/rpm (yum не проверялся, но dnf на EL8+/9/Fedora/Amazon Linux 2023 - его прямой преемник и обязателен в этой ветке), `alpine` -> apk. На apk-ветке `pkg_autoremove_list_empty`/`pkg_autoremove` - фактически no-op (`apk del` уже сам убирает осиротевшие зависимости, аналогично dnf-ветке), а имя пакета `ansible-core` не проверялось на реальном Alpine (см. открытый вопрос про имена пакетов в "Целевые дистрибутивы"). Всё остальное - явный "not supported" с сообщением и exit 1, ничего не гадаем.
- Cleanup после прогона (см. AI-readme.md "Using it on an already-installed Linux machine"): скрипт запоминает, были ли `git`/`ansible-core` установлены ДО его запуска, и после прогона плейбука purge'ит только то, что сам поставил. Пакеты, установленные ролями плейбука (например через `base`), не трогаются - это фактический результат работы плейбука, а не bootstrap-обвязка.
- Autoremove/cache cleanup: `scripts/manual.sh` также фиксирует в начале, пуст ли список "ненужных больше" пакетов (`apt-get -s autoremove` / `dnf -y -q repoquery --unneeded`). Если был пуст - после прогона запускает autoremove, зная, что все появившиеся orphan-пакеты (включая весь Recommends-хвост `ansible-core` на apt) появились именно из-за этого запуска. Если список НЕ был пуст изначально - autoremove не запускается вовсе, чтобы не трогать чужие orphan-пакеты, про которые мы ничего не знаем. Кеш пакетного менеджера чистится безусловно в конце (`apt-get clean` / `dnf clean all` / удаление `/var/cache/apk/*`) - это не установленное состояние, только скачанные файлы. На dnf-ветке проверено эмпирически (Rocky Linux 9), что `dnf remove` уже сам чистит свои transitive-зависимости при удалении (`repoquery --unneeded` пуст и до, и сразу после removal без отдельного autoremove) - в отличие от apt, где `purge` явно оставляет orphan'ы до отдельного `autoremove`. Из-за этого шаг `pkg_autoremove` на dnf (и, по аналогии, на apk) почти всегда no-op, но оставлен для единообразия логики между ветками и как страховка на случай сторонних orphan'ов.
- Проверено эмпирически на apt-ветке на трёх сценариях (Ubuntu 26.04, до отказа от cloud-init в скрипте, но сама логика cleanup не изменилась): чистая машина (всё ставится и всё чистится, 0 orphan-пакетов после), машина с заранее установленным `git` (сохраняется, `ansible-core` и весь его Recommends-хвост всё равно корректно убираются через autoremove), машина с посторонним pre-existing orphan-пакетом (autoremove корректно пропускается, чужой orphan не трогается, сам `ansible-core` при этом всё равно purge'ится explicit-веткой). На dnf-ветке (Rocky Linux 9) проверены сами `pkg_*`-примитивы (install/purge/autoremove-check/clean) по отдельности. apk-ветка частично проверена на реальной Alpine-машине пользователем: `pkg_*`-примитивы отработали корректно, `scripts/manual.sh` успешно поставил `git`/`ansible-core`. Этот же прогон (дефолтные `ROLES=base,extended`, без `nginx`) и обнаружил исходную проблему с `apk`/`community.general` (см. ниже) - сам фикс для неё пока проверен только в Docker smoke-тесте (`BASE_IMAGE=alpine:latest`), не переподтверждён повторно на реальной машине.
- **Самоудаление `ansible-core` из самого Ansible-плейбука невозможно и не реализуется.** Проверено эмпирически дважды (отдельно и вместе с `autoremove` в одной задаче) на apt: `ansible.builtin.apt: name=ansible-core state=absent` на apt/dpkg-уровне отрабатывает успешно (подтверждено через `module_stdout` - пакет реально удалён), но обработка результата самим Ansible после этого падает с `Module result deserialization failed: Unknown profile name 'module_legacy_m2c'` и повреждённым `sitecustomize.py` (`ModuleNotFoundError: No module named 'apt'`) - ровно в момент, когда dpkg обрабатывает удаление ansible-core. Задача, а с ней и весь прогон `ansible-pull`, помечается как **failed**, хотя фактическое изменение прошло успешно. Это хуже, чем не чистить вообще - каждый bootstrap выглядел бы сломанным. Поэтому весь cleanup (purge/autoremove/clean) живёт в `scripts/manual.sh`, который запускается как обычный процесс уже после того, как `ansible-pull` полностью завершился - там проблемы "самоудаления во время выполнения" не существует.

## Решённые вопросы

- Final-стадия (`cloud-init modules --mode=final`) тестируется всегда: и `packages:`, и исполнение `runcmd:` (через `scripts_user`) живут именно в этой стадии на обоих проверенных списках модулей (Ubuntu, AWS), см. раздел "Тестирование" выше.
- Модуль `ansible` (`cc_ansible`) не используется вовсе - вместо него `packages:` + `runcmd:` с обязательным `set -e`, см. раздел "Установка Ansible".
- `run_user`/PATH-фикс/`apt_get_command`-баг - вопросы, специфичные для `cc_ansible`, неактуальны с отказом от этого модуля (см. историческую справку в "Установка Ansible").
