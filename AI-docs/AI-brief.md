# ТЗ: Git-based bootstrap Linux VPS через cloud-init и Ansible

Название проекта и репозитория - `cloud-init-ansiblepull` (remote: `github.com/nvsmirnov/cloud-init-ansiblepull`).

## Цель

- Разработать небольшой публичный Git-репозиторий для начальной конфигурации Linux VPS.
- Использовать `cloud-init` только как bootstrap-механизм.
- Основную повторяемую конфигурацию выполнять через Ansible в pull-модели с `ansible-pull`.
- Сохранить минимальную сложность проекта и возможность в дальнейшем добавлять Ansible-роли.
- Реализовать локальный integration/smoke test в Docker без `--privileged`, без systemd и без полноценной виртуальной машины.
- Проект не нацелен на один дистрибутив. Минимальный набор, который должен поддерживаться в перспективе - свежие Ubuntu, Debian, RHEL-семейство, Amazon Linux, Alpine. Для этого предпочтение отдаётся простым, портируемым Ansible-фичам, см. AI-spec.md. Начальная целевая ОС, для которой сейчас реализованы production-шаблоны и smoke-тест — Ubuntu 26.04 LTS, остальные дистрибутивы - задача на будущее.
- Запускаться должно в виде curl -sSf --retry ... -o run.sh https://github-repo && bash bootstrap.sh (не буквально, с сохранением всех best practice). Для VPS это не понадобилось - весь bootstrap закрывается через user-data (`packages:` + `runcmd:`, см. AI-spec.md), без отдельного скрипта. Но этот же паттерн (curl -o -> bash) пригодился для generic-Linux кейса ниже, см. `scripts/manual.sh`.
- Должен быть простой механизм для указания дополнительны ролей.
- Тот же механизм (тот же репозиторий, тот же playbook) должен поддерживать не только VPS, но и преднастройку обычного (generic) Linux, уже установленного не через cloud-init at boot. Пример: новый ноутбук, на котором не хочется руками настраивать базовые вещи. Реализовано как `scripts/manual.sh`: curl-скачал -> запустил, см. AI-spec.md. Скрипт напрямую запускает `ansible-pull` (без cloud-init), сам ставит git/ansible-core только если их ещё нет, и убирает за собой именно то, что сам поставил (не трогая то, что было до него, и не трогая то, что установят роли плейбука).
- Как я понял, сейчас нет универсального механизма по переедаче каких-то параметров в дополнение к user-data. Если всё так - не нужно усложнять, просто создадим несколько шаблонов user-data в git, главное что их содержимое должно быть максимально простым и коротким (тут не используем моё требование по cleanup()). Подтверждено: bootstrap-логика полностью закрывается штатными ключами cloud-init (`packages:`+`runcmd:`), отдельный bootstrap.sh не нужен, см. AI-spec.md.

## Основная архитектура

- VPS получает обычный `cloud-init user-data`.
- `cloud-init` устанавливает только bootstrap-зависимости, необходимые для запуска Ansible.
- Ansible ставится штатным пакетным менеджером дистрибутива через top-level ключ `packages:` (`packages: [git, ansible-core]`), а не через модуль cloud-init `ansible` (`cc_ansible`) и не через pip. Модуль `ansible` отброшен после того, как на реальном AWS-образе (Amazon Linux) обнаружилось, что его вообще нет в списке модулей `cloud_final_modules` этого образа - user-data с ключом `ansible:` там молча ничего не делает, при этом `cloud-init status` рапортует полный успех. `packages:` и `runcmd:` (см. ниже), в отличие от `ansible`, присутствуют в списке модулей и на Ubuntu, и на AWS - это старые, универсальные ключи cloud-init. Детали и путь, которым пришли к этому решению (включая более раннюю попытку через pip и `install_method: distro`), см. AI-spec.md.
- После установки Ansible `cloud-init` запускает `ansible-pull` напрямую через `runcmd:` (обязательно с `set -e` первой строкой - без него упавший `ansible-pull` не прерывает скрипт и не отражается в `cloud-init status`, проверено эмпирически).
- `ansible-pull` получает конфигурацию из Git-репозитория.
- Репозиторий должен поддерживать выбор Git revision через отдельный параметр.
- Production-конфигурация должна позволять pin на полный commit SHA. Пока не реализуем: на старте два шаблона, `base.yaml` (`checkout: main`) и `base-dev.yaml` (`checkout: dev`). Pin на SHA - усложнение на будущее, если потребуется, см. AI-spec.md.
- Не использовать `curl | sh`.
- Не использовать Ansible push-mode, SSH inventory, Terraform provisioners, Packer, LXC/LXD или systemd для реализации этого проекта.
- Не требовать постоянно работающего агента или сервиса на сервере.
- если cloud-init из коробки может сделать всё что нужно для запуска ansible - можно положиться на это вместо curl bootstrap.sh
